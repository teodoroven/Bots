# Политика безопасности

Этот репозиторий содержит публичную портфолио-версию Python-бота для автоцентра/автошколы с Telegram/VK-интеграциями, GPT-функциями, SQLAlchemy-хранилищем, Alembic-миграциями и Docker-сценарием с PostgreSQL.

Не публикуйте детали уязвимостей в GitHub Issues, Discussions или Pull Requests.

---

## Как сообщить об уязвимости

Сообщайте об уязвимостях приватно через вкладку **Security** и действие **Report a vulnerability**, если оно доступно для репозитория.

Если приватная отправка недоступна, создайте публичный issue только с просьбой предоставить приватный канал связи. Не включайте в публичный issue технические детали уязвимости.

В публичных сообщениях не указывайте:

- exploit details;
- токены и API-ключи;
- пароли и строки подключения;
- `chat_id`, `user_id` и пользовательские данные;
- логи;
- дампы баз данных;
- вложения;
- скриншоты с приватной информацией;
- proof-of-concept payload.

В приватном отчёте полезно указать:

- затронутый файл, модуль или компонент;
- шаги воспроизведения;
- ожидаемое и фактическое поведение;
- возможное влияние;
- требуется ли доступ к настоящим Telegram, VK, GPT или database credentials.

---

## Что считается проблемой безопасности

Для этого проекта security issue включает:

- утечку Telegram bot token, VK token, GPT/API key, database credentials или Docker secret;
- попадание в репозиторий `.env`, `.secrets`, логов, вложений, voice/files, SQLite-баз, PostgreSQL dumps, `users/` или `chats/`;
- обход административных прав;
- выполнение admin-действий обычным пользователем;
- раскрытие приватных сообщений, имён, телефонов, `chat_id` или `user_id`;
- небезопасную обработку callback data, attachments, voice или document files;
- SQL injection;
- path traversal;
- небезопасную десериализацию;
- выполнение команд через пользовательский ввод;
- Docker/deployment configuration, раскрывающую credentials или запускающую сервис с лишними правами.

Обычные bugs, замечания по стилю, feature requests, падающие тесты без security impact и локальные ошибки конфигурации без утечки данных обычно не считаются уязвимостями.

## Секреты и runtime-данные

В репозитории должны оставаться только исходный код, миграции, публичные JSON-ресурсы, документация и безопасные примеры конфигурации.

Не коммитьте:

- реальные Telegram/VK/GPT токены и API-ключи;
- database passwords и production connection strings;
- реальные `chat_id`, `user_id`, имена, телефоны и историю сообщений;
- `.env`;
- `.secrets`;
- `logs/`;
- `attachments/`;
- `voice/`;
- `files/`;
- `users/`;
- `chats/`;
- локальные SQLite-базы;
- временные тестовые базы;
- PostgreSQL dumps;
- production backups.

Безопасные примеры конфигурации должны находиться только в `.env.example`.

Для Docker/server-сценариев используйте Docker secrets или переменные окружения платформы развёртывания. `docker-compose.yml` не должен хранить реальные пароли или токены.

---

## База данных и миграции

Проект использует SQLAlchemy и Alembic.

Миграции должны описывать схему базы данных, а не переносить runtime-данные.

Не добавляйте в миграции, fixtures, тесты, JSON-ресурсы или документацию:

- настоящие токены;
- пользовательские данные;
- историю чатов;
- дампы баз данных;
- production-настройки;
- реальные строки подключения.

## Если секрет попал в репозиторий

Считайте секрет скомпрометированным, даже если репозиторий был приватным.

В этом случае:

1. Отзовите или перевыпустите секрет.
2. Удалите его из текущего состояния проекта.
3. Проверьте git history и публичные копии репозитория.
4. Обновите `.gitignore`, `.dockerignore`, тесты или документацию, чтобы утечка не повторилась.
5. Задокументируйте mitigation, если это влияет на пользователей или deployment.

Удаления файла из последнего commit недостаточно, если секрет остался в истории.

## Проверки перед публикацией

Перед публикацией или release-изменениями запустите:

```bash
git diff --check
python -m compileall -q main.py relay bots db tests
python -c "import main; import relay; import db.storage"
alembic upgrade head
python -m unittest discover tests -p "*_test.py"
```
